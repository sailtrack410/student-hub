# App 功能补齐与优化清单（2026-10-21）

> **范围**：`app/` Flutter 学生端（Android/Web；iOS 未建工程）  
> **排序原则**：先补齐“页面存在但链路没闭环”的功能，再做性能/稳定性/安全优化，最后做 UI/HIG。  
> **依据**：当前源码静态盘点 + 2026-10-18～20 验收截图 + 已有后端接口。  
> **UI 专项**见 [2026-10-21-App-Apple-HIG设计评审](2026-10-21-App-Apple-HIG设计评审.md)，本清单只列顺序，不重复展开 UI 细节。

## 一、先划清“已完成”和“没闭环”

### 已经可用、不要重复做的

- QQ 登录、首页 BFF、服务目录/详情、动态表单、通知列表、教务认证、课表、成绩、电费、作业中心。
- 社区帖子流/详情/发帖/评论/点赞/举报/申诉、私信、AI 基础问答与 SSE、勋章墙/佩戴、登录设备管理、隐私偏好。
- 广告位、曝光/点击/落地、开屏广告、应用更新下载。

### 真正要补的是“页面有了，但数据或动作还是演示/假值”的链路

| 现象 | 证据 | 影响 |
|---|---|---|
| “我的申请”列表是演示卡 | `app/lib/pages/service/my_requests_page.dart:449` 明确写“演示数据：真实工单列表接口接入后自动替换”；筛选计数写死 3/1/1/1，只取了第一条真实申请用于催单 | 学生看不到自己的真实申请列表，事务闭环不成立 |
| “工单详情”是演示工单 | `app/lib/pages/service/work_order_detail_page.dart:190` 写“演示工单”；师傅姓名/电话/时间轴/工单号均为默认值或硬编码；分享按钮 `onPressed: () {}` | 进度追踪、催单、验收都是“看起来能用” |
| 报修表单的现场照片是假字符串 | `app/lib/pages/service/repair_apply_page.dart:36` 初始 `['故障现场']`，`:246-257` 只是往列表里加“现场特写 N”，没有调用相册/相机，也没有上传 | 报修最关键的证据照片缺失 |
| 通用申请表单跳过图片字段 | `app/lib/pages/service/service_apply_page.dart:143-145` 对 `type == 'image'` 直接 `continue`，注释写“图片上传链路尚未接入” | 所有带图片字段的服务事项都提交不了完整材料 |
| 系统推送未接 | `app/lib/services/system_notification_io.dart:1-3` 是空实现；`settings_security_page.dart` 的推送开关只保存偏好，没有注册 FCM/APNs Token；后端 `AppPushDeliveryController.java:18` 明确写“当前 App 尚未接入系统推送” | 后台推送任务 clicked 永远为 0，用户收不到系统通知 |
| 一卡通/图书馆是占位 | `app/lib/pages/profile/profile_page.dart:811` 一卡通充值 `toast('一卡通充值即将开放')`；`:819` 图书馆借阅同样 | 个人中心展示“¥86.50 / 2 本”但数据是硬编码，点进去没有功能 |
| 社区删帖/表情/分享未闭环 | 后端已有 `DELETE /api/app/community/posts/{postId}`（`AppCommunityController.java:91`），App 端没有调用入口；发帖表情按钮 `post_publish_page.dart:1055` 是空 `onPressed`；工单分享空实现 | 用户发错内容不能自删；发帖工具不完整 |
| 登录/启动仍是开发态 | `main.dart:57-72` 自动 dev 登录 + mock 李同学；登录协议默认勾选且不可点 | 不是真实用户体系，不能上线 |

> 结论：**功能补齐的第一优先级不是“再画新页面”，而是把这 6 条主链从演示态改成真实态。** 其中“我的申请/工单详情”和“图片上传”是事务办理的核心，优先级最高。

## 二、功能补齐清单（按依赖与价值排序）

### F0 核心事务闭环（最高优先）

#### F0-1 我的申请 + 工单详情接真实数据

- **现状**：列表演示卡、计数写死；详情硬编码；报修提交成功后不接后端返回的 `requestId`，直接跳到硬编码的 `WO-20261017-0915`；评价/驳回仍把 `orderNo` 当 `requestId`/`workOrderId` 传入，真实数据下存在参数不匹配风险。
- **要做的**：
  1. `MyRequestsPage` 改为真实分页列表：状态筛选（全部/处理中/待验收/已办结）、下拉刷新、加载更多、空态/失败重试；计数由接口返回或按状态统计。
  2. `WorkOrderDetailPage` 用 `fetchRequestDetail(requestId)` 拉取真实详情，渲染申请信息、工单状态、师傅、时间轴、照片；去掉“演示工单”横幅。
  3. 统一 ID 语义：申请 `requestId`、工单 `workOrderId` 分开传递；评价用 `requestId`、退回/确认用 `workOrderId`；写契约测试。
  4. 动作闭环：撤销申请、催单（含冷却提示）、确认完工、退回重办、评价；操作后刷新列表和详情。
  5. 真实电话从详情接口取，不再硬编码 `13981685210`。
- **涉及文件**：`pages/service/my_requests_page.dart`、`pages/service/work_order_detail_page.dart`、`pages/service/evaluation_sheet.dart`、`api/service_request_api.dart`。
- **验收**：用真实账号走“提交申请 → 我的申请看到 → 详情看到 → 催单 → 完工 → 评价”，每一步数据来自接口；断网有失败态，不落回演示卡。
- **估算**：3–5 天（含接口对齐/异常态）。

#### F0-2 服务申请/报修的真实图片上传

- **现状**：`image_picker`、`ApiClient.uploadImage`、`/api/app/files` 都已存在，但两个表单都没用；报修页面还预填了演示描述、姓名、电话。
- **要做的**：
  1. 接入 `image_picker`（相册/相机），压缩后 `uploadImage` 拿 `fileId`，再随表单提交。
  2. 图片网格支持预览、删除、重试、数量上限（报修 3 张、通用表单按 schema），上传中显示进度/禁用提交。
  3. `type == 'image'` 的字段接入真实上传，不再 `continue`；必填图片缺失时字段级报错。
  4. 清理演示预填：手机号从当前用户资料带出，描述留空，`_photos` 初始为空；不落库的联系人字段不保留。
- **涉及文件**：`pages/service/service_apply_page.dart`、`pages/service/repair_apply_page.dart`、`api/api_client.dart`、`services/image_compressor.dart`。
- **验收**：从相册选图 → 预览 → 提交 → 后台详情能看到图片 URL；取消/失败/超限都有提示；不选必填图不能提交。
- **估算**：1–2 天。

#### F0-3 登录与启动的真实态（上架门禁）

- **涉及文件**：`main.dart`、`pages/login/login_page.dart`、`api/auth_service.dart`、新增隐私页/路由。

## 三、优化清单（功能闭环之后）

> 优化不是“UI 美化”；这里指性能、稳定性、数据一致性、安全。UI 在下一节。

### O1 真实数据下的状态与异常

- 每个列表页统一：首屏 loading、下拉刷新、加载更多、空态、失败重试、401 回登录；禁止“接口失败落回演示数据”。
- 表单提交：按钮防重复、请求超时、失败保留草稿、成功后刷新列表；图片上传失败可重试。
- 详情页：404/已删除/无权限三种状态分开，不要统一显示空白。
- **验收**：断网/超时/401/空数据四种场景逐页走查。

### O2 性能与启动

- 启动链路去掉 dev 登录等待；本地会话校验与首页 BFF 并行；首屏骨架屏不要等所有接口。
- 列表统一 `ListView.builder`/分页，避免一次性构建全部评论/通知；图片列表用缩略图 + `cacheWidth`。
- 图片上传前压缩（已有 `image_compressor.dart`），限制尺寸/质量；服务端返回短时 URL 时做本地缓存。
- AI SSE 断线重连/取消；WebSocket 重连退避；离开页面取消订阅。
- 版本检查统一走 `AppUpdateService`，删掉设置页“当前已是最新版本”的假 toast。

### O3 数据一致性与契约

- 统一 `requestId` / `workOrderId` / `orderNo` 语义；评价、退回、确认、催单分别用自己的 ID。
- 状态枚举以后端为准，客户端不要用文案/魔法字符串判断；筛选计数由接口或统一统计得出。
- 操作成功后本地列表/详情同步刷新，避免“提交成功但列表还是旧数据”。
- 补 API contract tests（MockMvc + Flutter 单测），覆盖 401、404、重复提交、冷却期。

### O4 安全与发布

- 移除 release 的 dev 登录/mock 会话；清理演示姓名/电话/描述；日志不打印 token/手机号。
- 隐私政策、权限说明、第三方 SDK 清单（QQ/推送/广告/地图）与代码一致；提供数据删除/撤回入口。
- Token 存储、退出登录、设备下线、越权访问逐项回归。
- 发布前跑 Android release 包 + 真机，不以 debug 包验收。

### O5 可观测性与测试

- 关键链路埋点：登录、提交申请、工单状态、评价、推送点击；后台已有广告/推送指标，补业务漏斗。
- Flutter widget test 覆盖：登录协议、表单图片必填、申请列表空/失败态、工单详情状态映射。
- E2E：真实账号走“申请 → 列表 → 详情 → 催单 → 验收/评价”。

## 四、UI 清单（最后做，按 HIG 报告执行）

## 六、需要产品/你拍板的 5 件事

1. **我的申请/工单详情**：学生端是否只查看与验收，不处理派单？确认后按该状态机接真实接口。
2. **一卡通/图书馆**：短期隐藏，还是已有校方接口可以接？没有接口就不要展示假余额。
3. **系统推送**：目标渠道是 FCM、APNs，还是国内厂商推送？这决定客户端 SDK 和后端凭据。
4. **社区**：帖子作者自删是否开放？表情面板是否本期做？消息中心“AI待办”保留吗？
5. **iOS**：本轮只做 Android，还是 iOS 也进 Q4 排期？若进，Sign in with Apple 和隐私清单要提前。

## 七、完成定义（DoD）

- 功能：所有入口点下去有真实结果或明确“未开通”说明，不再出现“演示数据/即将开放”的空链路。
- 优化：断网/超时/401/空数据/重复提交都有确定行为；真实账号全链路可复现。
- UI：HIG 报告的 P0/P1 项关闭；iPhone/Android 各一台真机验收。
- 发布：release 包无 mock/dev 登录；隐私政策可达；Android 签名包可安装；iOS 另走独立清单。
