# 竞品「绵城助手」可取之处清单

对标对象：**绵城助手**（`com.mycc.helper`，v1.0.16 / version_code 16）——面向绵阳城市学院的第三方校园 App，Flutter 客户端 + Laravel 服务端，实测 81 条路径、43 个接口可用。

**定位差异是本文的前提。** 对方是**非授权第三方**：数据靠用户自持凭据代抓（教务会话 cookie 由服务端持有并随响应回传客户端），获客依赖违规手段（宿舍打卡的位置模拟、时间随机化、人脸照片轮换、云端代签），其官方 changelog 已在 1.0.16 主动写下「移除了晚间查寝打卡」。我方是**校园授权**：数据来自校方接口对接，产品是"申请—派单—办结—评价"业务闭环 + AI 助手。

因此本文只收录**在授权定位下正当、可借鉴**的部分；凡依赖"伪造 / 规避 / 绕过"的机制，一律进第五节排除清单并写明理由——那一节同时也是决策记录，日后有人提"竞品有我们也要有"，可直接引用。

**结论先给**：值得借鉴的共 **15 项**——功能缺口 8 项（其中成绩/考试查询性价比最高）、接口设计 4 项、工程做法 3 项；明确排除 5 项。

---

## 一、功能层可取之处（8 项）

### 1.1 成绩查询 + 学业统计（P0）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /jwgl/grades` |
| 响应结构 | `student{studentId,name,college,major,className,educationLevel}` + `totalCourses:18` + `totalCredits:44.5` + `passedCredits:44.5` + `averageScore:81` + `passedCount:18` + `failedCount:0` + `terms[]`（按学期分组，每学期带 `coursesCount/termCredits/courses`） |
| 我方现状 | **完全没有成绩模块**（全仓库搜 `成绩 / grade / exam` 仅命中 `docs/评测/RAG/corpus/transcript-notice.md` 的"成绩单办理须知"文案与管理端设计稿假数据） |
| 借鉴方式 | 复用现有青果教务会话（`modules/jwauth` 的 `JwSessionStore` + `integration/jw/KingosoftScheduleClient`）多抓一个页面，边际成本极低 |

**关键判断：必须连聚合统计一起做，不要只搬原始分数表。** 学生真正要看的是"挂了几门、还差多少学分、平均分多少"，对方把 `passedCredits / failedCount / averageScore` 在服务端算好，这个取舍是对的——把它放到端上算，意味着小程序、管理端、AI 助手各算一遍。

**一并规划成绩发布提醒**：对方 `settings` 里有 `notify_grade_reminder` 开关（其 APK 内含腾讯 TPNS 推送通道），说明"成绩出了要通知"确有需求；我方做这件事的差异不在功能而在**数据来源正当、推送内容可信**，可与成绩查询同批规划。

### 1.2 考试查询（P0，与 1.1 同批动工）

对方 `GET /jwgl/exams` 有一处建模值得照抄：**考试是按轮次组织的**，学期不是唯一维度——

```
examRound: "1", examRoundName: "2026-2027学年第一学期开学补考",
availableRounds: [{code:"1", name:"2026-2027学年第一学期开学补考"}],
availableTerms: [{code:"20260", name:"2026-2027学年第一学期"}],
isEmpty: true, totalCount: 0, exams: []
```

若只按学期建表，补考/期末/缓考这类安排会互相覆盖。同一批抓取几乎不增加成本，建议和成绩一起做。

### 1.3 调停课的变更表达（P1）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /jwgl/adjustments`（实测 13 条） |
| 条目结构 | `actionType(停课\|补课)` + `details[{item, before, after}]`（item 可为周次/节次/地点/教师）+ `targetClasses` + `reason` + `summary` + `noticeTime` |
| 我方现状 | `modules/schedule/job/ScheduleSyncWorker` 已做班级课表 diff 并发"课表更新提醒"，但输出只到"课程有变化"这一层 |
| 借鉴方式 | 把 diff 结果按 `details` 的 item/before/after 三元组输出 |

**价值**：现在的提醒只能说"你的课表有更新"，学生还得自己去找哪节课变了。用三元组表达后，通知正文可以直接是"《数据库原理》第 8-10 周由周三 3-4 节调至周五 5-6 节"——学生一眼能判断要不要改行程。这是**数据模型层面的借鉴，不是功能复制**，而且对方的 `actionType` 区分停课/补课也值得一并保留。

### 1.4 公告发布与管理端入口（P1）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /messages/announcements` + `announcements/summary` + `announcements/read-all` |
| 字段设计 | `type` / `priority` / `is_pinned` / `official` / `identity`（如"绵城助手官方"）/ `label`（如"系统公告"）/ **`effective_at` + `expires_at`** / `is_read` |
| 我方现状 | notification 模块基建完整（发送/列表/未读/已读），但**没有管理端公告发布入口**（无 `AdminNotificationController`），且通知表无生效期概念 |
| 借鉴方式 | ① 加管理端发布入口；② 表增 `effective_at / expires_at / priority / pinned / official` 字段；③ 加一个 summary 接口喂首页卡片 |

**为什么优先级高**：授权定位下，公告是校方最标准的宣传渠道，也是这个项目相对第三方 App 的天然优势面。对方的公告支持定时上下线与官方身份标识，说明这些字段是真实运营中长出来的需求，不是设计过度。`summary` 接口（返回 `latest` 摘要 + `unread_count`）用于首页小卡，避免首页为一个角标拉整列表——这个拆分方式可以直接照搬。

### 1.5 客户端版本上报 + 远程配置（P1）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /app/config` + `GET /app/check-update`，并强制客户端每次请求带 `x-app-version-code: 16` |
| 关键字段 | config：`developer_mode / allow_account_deletion / community_posting_enabled / community_commenting_enabled`；check-update：`has_update / version_name / min_version_code / force_update / changelog / apk_url / sha256 / file_size` |
| 我方现状 | **核实无任何版本上报或远程开关机制**（全仓库唯一相关代码是 `student-hub-weapp/pages/login/index.js:14` 本地判断 `envVersion === 'develop'` 的调试入口） |
| 借鉴方式 | ① 小程序启动时上报 `version / envVersion`，服务端记录版本分布；② 加远程开关接口（`RAG_ENABLED` 这类改环境变量重启的开关改为可热改）；③ 用微信 `updateManager` 实现强制更新 |

**为什么值得做**：微信小程序的更新时机不可控（受微信调度），服务端不知道用户跑在哪个版本，就无法安全地做接口变更与灰度。对方把版本号做成强制请求头，是这类产品的基础设施而非可选项。

### 1.6 匿名发帖：前台匿名 + 后台实名（P2）

| 维度 | 内容 |
|---|---|
| 对方字段 | 帖子带 `is_anonymous` + `real_author_id`（**服务端保留真实作者**）+ 用户设置 `hide_real_name` |
| 我方现状 | **无任何匿名机制**（搜 `anonymous / 匿名` 仅命中文件签名的"匿名访问"，与社区无关） |
| 借鉴方式 | 社区帖子增 `is_anonymous` 标记，作者字段全量落库不变，仅在出参层对他人隐藏 |

**这条特别契合授权定位。** 校园社区需要匿名表达（学生不敢实名问敏感问题），而授权平台必须"前台匿名、后台实名可追溯"——这正好是校方能接受、且比一刀切禁止匿名更好的做法。对方作为第三方都做了服务端留真身，我方有授权身份更应做对：**匿名只作用于展示层，不作用于存储层**，配套在社区公约里写明"匿名仅对同学匿名，校方可依规追溯"。

### 1.7 搜索 + 热搜（P2）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /search?q=&type=&page=`（`q` 必需）、`GET /search/hot`（`keyword/searches/rank`，7 天窗口）、`GET /users/mention-search?keyword=` |
| 我方现状 | 只有社区列表内的 `keyword` 过滤（`AppCommunityController.java:44-47`），**无跨域全局搜索** |
| 借鉴方式 | 先做跨域搜索（帖子 + 服务事项 + 知识库文档）；热搜用真实搜索日志按周期聚合 |

**注意取舍**：热搜是需要真实流量支撑的功能，我方当前体量下不要做"人工热搜"（那会变成运营造假）。建议先只做搜索 + 搜索日志落库，等日志有量再开放热榜。`mention-search`（@ 候选）在已有私信与社区回复的场景下是补齐体验的小件，可一并做。

### 1.8 课程签到/考勤的正规版本（P3，需校方决策）

| 维度 | 内容 |
|---|---|
| 对方接口 | `/course-checkin/*`（独立子系统：`login / session / active-tasks / submit / reminders / locations`），签到手段为 N 位数字签到码、二维码、教室 GPS 点位、校园网网关探测 |
| 我方现状 | 无任何签到/考勤能力 |
| 借鉴方式 | 手段本身中立，可做**教师发起点名 + 教室地点围栏 + 限时数字码**；**明确不做自动签到与代签** |

**与对方的分界线在"谁发起、能否代签"**：对方把签到做成"服务端云端代提交 + 位置时间人脸三重模拟"，那是伪造考勤；而校方授权下的点名是正当教学管理功能。注意这条要立项需校方决策（牵涉教务管理职责），不建议我方单方面推。

## 二、接口设计可取之处（4 项）

### 2.1 错误码补"上游故障"独立态（P1）

| 维度 | 内容 |
|---|---|
| 对方错误码 | 四态：`JWGL_UNBOUND` / `JWGL_BINDING_INVALID` / `JWGL_CREDENTIAL_INVALID` / **`JWGL_TIMEOUT`**（文案「教务系统连接超时」） |
| 我方现状 | 两态：`ErrorCode.java:33-34` 的 `JW_401_01`（认证失败）/ `JW_401_02`（会话失效） |
| 借鉴方式 | 增一个上游故障/超时码 |

**为什么这是实际问题**："教务系统连不上"和"你的密码错了"对学生的行动要求完全不同——前者应该提示"稍后再试"并保持绑定状态，后者要引导"去重新绑定"。混在一个码里，前端只能给模糊文案，客服也无法区分工单类型。教务系统本就经常抽风，这个码在运维侧价值更高。

### 2.2 社区帖子流的增量同步（P2）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /posts/sync?cursor=&limit=` |
| 响应结构 | `events[{version, kind: post_added\|post_removed, post_id, post}]` + `next_cursor` + `latest_version` + `reset_required`（兜底全量） + `has_more` |
| 我方现状 | 社区未读数靠 15 秒轮询（`student-hub-weapp/app.js:61-66,75-92`） |
| 借鉴方式 | 帖子流改为版本游标增量拉取，`reset_required` 时回退全量 |

**设计要点**：它用 `version` 单调递增游标 + 事件类型（新增/删除）表达变化，而不是让客户端对比全量列表——删帖、审核下架这类"消失"的变化也能被准确传达，这是纯轮询做不到的。`reset_required` 字段是必要的逃生口（服务端数据重整时让客户端重新全量），这个细节很多人会漏。

### 2.3 未读聚合接口 + 通知偏好开关（P2）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /messages/unread-count` 一次返回 `{unread_count, direct_messages, replies, mentions, announcements}`；`/auth/settings` 内含按事件分开关的偏好：`notify_class_reminder / notify_checkin_reminder / notify_course_checkin_reminder / notify_grade_reminder / notify_schedule_change` |
| 我方现状 | notification 与 community 的未读各自查询（要发多次请求）；**无通知偏好开关**（搜 `notifyPref / 通知偏好` 零命中） |
| 借鉴方式 | ① 聚合成一个未读接口喂 tab badge 与四个入口；② 用户表或其附属表增按事件类型的订阅偏好 |

**未读聚合**的价值是请求数：tab badge 需要全站未读，现状下每进一次前台就要并行发好几个请求。**通知偏好开关**的价值是减少无效通知——课表变更提醒、成绩提醒、社区回复应能让用户单独关。对方把开关粒度做到"按业务事件"（而不是一个总开关），这个粒度对我方更必要，因为我们的通知类型比它多。

### 2.4 批量接口 + 展开逻辑下沉（P2/P3）

| 维度 | 内容 |
|---|---|
| 对方接口 | `GET /posts/view-counts?ids=1&ids=2...`（批量浏览量）、`POST /posts/cache-validate`（批量缓存校验） |
| 对方形态 | 课表直接返回 `matrix`（星期 1-7 × 6 个时段槽位 = 42 格），前端拿来即渲染 |
| 我方现状 | 课表返回扁平列表 + `firstMonday/totalWeeks`（`ScheduleViewResponse.java:7-16`），矩阵由小程序端自行拼；无批量查询接口 |
| 借鉴方式 | ① 列表页的计数类字段提供批量接口；② 服务端出"当日课程/下一节课"视图接口 |

**展开逻辑下沉是这里最值钱的一条**：现在只有一个小程序端在拼矩阵所以没感觉，但 AI 助手要回答"我今天有什么课"、管理端要做课表视图时，这套"周次 + 节次 → 排布"的逻辑就要写第两遍第三遍。建议服务端先把"当日课程"这一个视图做出来（AI 助手与首页都要用），矩阵整表可以暂不做。

## 三、工程做法可取之处（3 项）

### 3.1 提交前的资格校验顺序（P1）

对方的签到流程里有一个交互顺序值得学：**先 `POST /dorm-checkin/location/verify` 校验资格（返回 `inRange`），通过了才让用户填写内容**，而不是让用户填完表单再在提交时报错。

我方适用场景：服务申请（`modules/servicerequest`）目前是填完提交才知道是否符合条件。**把可前置校验的规则（是否在办理时间窗、是否已有在办同类申请、是否需要前置材料）做成"预检接口"，在进入表单前就告诉学生能不能办**——这能直接减少无效申请量与工单退回率，是业务价值而非体验细节。

### 3.2 原始值 + 归一化值双写（保持现有约定，无需改动）

对方每个课程对象同时返回原始与解析结果：`weekRaw`（如 `1-3,6-8[1-4]`）+ `weeks`（展开数组）、`sectionRaw` + `sections`。

我方 `ScheduleCourseEntity.java:35` 已有 `rawText` 字段——**这一点我们已经做对了，本文只是把它固化为约定**：今后解析类数据一律"原始文本 + 解析结果"双写。理由是教务原始格式会出意外形态（对方的 `weekRaw` 里就有 `[1-4]` 节次后缀、`'0'`、`'100'` 这类脏样本），只存解析结果等于无法回溯与重解析。

### 3.3 端上缓存按"数据 / 当前学期"分离（P3）

对方的客户端缓存分四个文件，其中值得注意的拆分是：`jwgl_schedule_local_cache.json`（数据）+ `jwgl_schedule_semester.json`（当前选中学期）分开存，调课数据同理。

我方课表落 MySQL、由服务端提供，等效性已经具备；若后续要做端上离线缓存（如弱网下看课表），按这个拆分方式存，不要把"数据"和"用户当前选择"混在一个对象里——否则换学期时会连带失效整个缓存。

## 四、对方没有、我方已有的部分（不必对标）

写进来是为了避免后续对标的焦虑式补功能：

- **AI 助手 + RAG 知识库**：对方完全没有（无任何对话、检索、知识库接口）
- **服务目录 / 申请—派单—办结—评价闭环 + 工单**：对方没有业务流，教务类接口全是只读代理
- **数据大屏与现场终端**：对方没有
- **教务会话安全**：我方 Redis + AES 加密、cookie 不出网关；对方把 `cookies` 随响应回传客户端（见 5.2）
- **学期切换能力**：对方 `availableTerms` 只返回当前学期，`?term= / ?academicYear= / ?semester= / ?semesterCode= / ?xnxq=` 实测**全部被忽略**——这是它的功能缺失，不是设计取舍
- **单双周支持**：我方有 `weekParity`（单/双周）语义；对方 `weeks` 只做逗号分段与连字符展开，无奇偶周概念
- **双学号在库中有独立字段**：我方 `jw_binding.sso_account`（统一身份）与 `jw_binding.jw_student_no`（教务内部学号）分列；对方是服务端黑盒映射

## 五、明确排除：不采纳的 5 项

| # | 机制 | 对方做法 | 排除理由 |
|---|---|---|---|
| 5.1 | 宿舍打卡的"四层模拟" | 位置模拟（坐标库随机选点）+ 时间随机化（22:00–23:00 内随机时刻）+ 人脸照片轮换（≤5 张随机挑）+ 云端服务端定时代提交 | **违规核心**。本质是伪造考勤，把产品做成作弊工具；对方官方已在 1.0.16 下架该功能 |
| 5.2 | 教务 cookie 回传客户端 | 所有 `/jwgl/*` 响应带 `cookies: "JSESSIONID=..."` | 凭据泄漏面扩大：端上被逆向即等于暴露教务会话。我方 Redis + AES、cookie 不出网关是正确的，保持不变 |
| 5.3 | 长期存储学号 + 密码做静默重登 | 会话失效后用加密存储的凭据自动重登 | 库被拖即全校教务密码。我方"会话失效 → 置 EXPIRED → 要求重新认证"是正确的安全取舍；若要减负，可做会话临期主动保活，不要存长期密码 |
| 5.4 | 批量评教 + 预设标签库 | `POST /evaluation/batch-evaluate`（按 `taskId/questionnaireId` 批量提交）+ `GET /evaluation/tags`（`PositiveTagList / NegativeTagList` 预置正负标签） | **教学数据造假**：模板化代填使评教数据失去意义。但"标签化快速评价"的交互本身可正当使用——由学生自己选标签加速填写，而不是替他选。**注意：评教是学生真实意愿表达，作为校方授权平台更应保证其真实性，这条必须排除** |
| 5.5 | 导出原样透传上游畸形产物 | `/jwgl/schedule/export` 把教务返回的 GBK 编码、伪装成 `.xls` 的 HTML 直接 base64 塞进 JSON | 技术债（非违规）：把上游的畸形格式透给客户端，客户端还得自己 base64 解码 + 处理 GBK。我方若做导出应生成标准格式——建议按 iCal（订阅进手机日历）或课表图片（发班级群）输出，价值高于 Excel |

> 说明：5.1 是违规机制，5.2/5.3 是安全债，5.4 是数据真实性红线，5.5 是技术债——排除理由性质不同，引用时请注意区分，不要笼统说"竞品的东西都不学"。
