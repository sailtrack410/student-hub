## 用例 1：评论发表接口 —— 失败必须可感知（P0-1 地基）

| | 内容 |
|---|---|
| 操作 | `POST /api/app/community/posts/{postId}/comments`，body `{"content":"本地联调测试：P0评论链路验证"}` |
| 出现的情况（修复前客户端行为） | 无论接口成败，客户端都插入一条本地捏造的评论（id=`comment_时间戳`、内容回填原文、timeAgo 硬编码「刚刚」），评论数+1，弹「评论发表成功」。**接口实际失败时刷新即消失，用户被骗**。 |
| 期望情况 | 接口返回 `success:true` 且 `data.commentId` 存在才视为成功；失败时客户端返回 null、不插入、不计数、保留输入。 |
| 实际情况（实测） | ✅ 接口成功返回 `commentId=2116102615465136129`、`content` 原文、`likeCount=0`、`liked=false`、`createdAt` 服务端时间。**`commentId` 字段真实存在**，新的 null 判据 `raw['commentId'] == null` 不会误杀成功响应。字段与 `_mapComment` 映射一一对应（commentId/authorName/avatarUrl/likeCount/liked/pinned/createdAt 均在）。 |

## 用例 2：评论点赞接口 —— 严格校验字段真实存在（P0-1 前置修复地基）

| | 内容 |
|---|---|
| 操作 | `POST /api/app/community/comments/{commentId}/like`，body `{}` |
| 出现的情况（修复前） | 客户端在已解包的 data 里找 `success` 字段（不存在）→ 恒 false → 乐观更新被回滚 + 弹「点赞失败，已恢复原状态」。**明明点赞成功却报失败**。 |
| 期望情况 | 客户端改按 data 内 `liked`（bool）/`likeCount`（num）校验，两个字段必须真实存在于响应。 |
| 实际情况（实测） | ✅ 响应 `{"success":true,"data":{"commentId":"...","liked":true,"likeCount":1}}`。`liked`/`likeCount` 字段齐全且类型正确。**幂等语义也实测通过**：同一评论连点两次 = 赞→取消（第二次返回 `liked=false, likeCount=0`），证明 toggle 语义正常，客户端「服务端权威覆盖」策略有可靠数据源。 |

## 用例 3：评论「最热/最新」排序（P0-2）

| | 内容 |
|---|---|
| 操作 | 造 4 条评论：P0 验证评论(1赞)、c1(1赞)、c2(0赞)、c3(0赞，先赞后取消回到 0)，拉详情接口模拟客户端排序视图 |
| 出现的情况（修复前） | `_isSortByHot` 只切换按钮加粗/颜色，`itemBuilder` 固定按 `_comments` 原序渲染，**列表纹丝不动**。 |
| 期望情况 | 最热 = 点赞数降序，同赞按 id 数值新在前；最新 = 服务端时间序倒转。排序只影响渲染视图，不改 `_comments` 存储。 |
| 实际情况（实测） | 服务端返回（时间正序）：`136129(1赞) → 064577(1赞) → 724161(0) → 578049(0)`。按客户端新逻辑推演：最热序 `064577, 136129, 578049, 724161`（1赞在前，同赞 id 新在前；0 赞组同样 id 新在前）；最新序 `578049, 724161, 064577, 136129`。**两组序列均与数据吻合，排序逻辑有真实数据支撑**。widget 测试同步验证切换不崩、列表稳定。 |
