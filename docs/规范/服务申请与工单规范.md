# 服务申请与工单闭环

## 全流程与流程配置

服务目录使用 `service_item.flow_type` 显式选择处理策略，申请创建时将 `flow_type` 与 `item_code` 保存到 `service_request`。目录改名、改编码或修改后续流程配置，不改变已提交申请的处理策略。禁止按事项名称或编码前缀推测是否需要维修派工。

| flowType | 提交与后续流程 | 适用范围 |
|---|---|---|
| `REPAIR` | 创建维修工单 → 派单 → 维修 → 验收/评价 | 明确配置为报修的事项 |
| `LEAVE_APPROVAL` | 待审批 → 已批准/待销假 → 管理端销假；另有驳回、撤回 | 请假申请；复用现有管理权限及组织数据范围 |
| `MANUAL` | 待受理 → 人工受理 → 人工办结；另有驳回、撤回 | 证明、场地等尚未接通专门业务能力的事项 |
| `GUIDE` | 只展示指南，不接受申请，不创建工单 | 咨询与指引 |

新建目录未指定流程时默认为 `MANUAL`，不自动创建维修工单。申请单兼容保留 `SUBMITTED / PROCESSING / COMPLETED / REJECTED / CANCELLED`；学生端优先展示 `businessStatus`、`statusLabel` 和服务端返回的 `availableActions`，不从通用状态推导维修按钮。

```text
REPAIR: 学生提交 → 维修工单待派发 → 调度派单 → 处理/照片 → 学生验收 → 评价
LEAVE_APPROVAL: 学生提交 → 有权限管理人员审批 → 管理端销假 → 已销假
MANUAL: 学生提交 → 有权限管理人员人工受理 → 人工办结
GUIDE: 阅读指南 → 按实际说明办理
```

请假不创建维修工单、不派师傅、不要求维修照片或学生确认完工。销假沿用管理端能力，不新增教师/辅导员关系或校方系统审批集成。人工办结只记录线下处理结果，不代表已实现电子出证、证明下载、场地资源占用或预约冲突检测。

每个动作写入 `service_request_log`，申请详情页时间线按时间正序展示。历史非报修工单通过归档标记退出维修操作队列，保留原始工单及审计记录，详见 [分流迁移与接口说明](../方案/2026-11-07-请假与报修分流迁移及接口说明.md)。

## 申请状态机（RequestTransitions）

| 动作 | 允许的来源状态 | 目标状态 |
|---|---|---|
| SUBMIT | 无 | `SUBMITTED` |
| APPROVE（请假审批通过） / ACCEPT（人工受理） | `SUBMITTED` | `PROCESSING` |
| LEAVE_CANCEL（管理端销假） | `PROCESSING` | `COMPLETED` |
| DISPATCH（仅维修派单） | `SUBMITTED` | `PROCESSING` |
| START（开始处理） | `PROCESSING` | `PROCESSING`（仅记录） |
| ARRIVAL_PHOTO（现场拍照） | `PROCESSING` | `PROCESSING`（仅记录） |
| COMPLETION_PHOTO（完工拍照） | `PROCESSING` | `PROCESSING`（仅记录） |
| CONFIRM（报修人确认） | `PROCESSING` | `PROCESSING`（仅记录） |
| REOPEN（退回重新处理） | `PROCESSING` | `PROCESSING`（仅记录） |
| COMPLETE（办结） | `PROCESSING` | `COMPLETED` |
| REJECT（驳回） | `SUBMITTED` / `PROCESSING` | `REJECTED` |
| CANCEL（撤销） | `SUBMITTED` / `PROCESSING` | `CANCELLED` |
| EVALUATE（评价） | `COMPLETED` | `COMPLETED`（仅记录，一次） |

## 工单状态机（WorkOrderTransitions）

| 动作 | 允许的来源状态 | 目标状态 |
|---|---|---|
| ASSIGN（派单/改派） | `PENDING_DISPATCH` / `ASSIGNED` | `ASSIGNED` |
| START | `ASSIGNED` | `PROCESSING` |
| RECORD_ARRIVAL_PHOTO（现场拍照） | `PROCESSING` | `ONSITE_PHOTO_RECORDED` |
| SUBMIT_COMPLETION（完工拍照并提交） | `ONSITE_PHOTO_RECORDED` | `PENDING_CONFIRMATION` |
| CONFIRM（报修人确认） | `PENDING_CONFIRMATION` | `COMPLETED` |
| REOPEN_CONFIRMATION（报修人退回） | `PENDING_CONFIRMATION` | `ONSITE_PHOTO_RECORDED` |
| COMPLETE（明确不需要拍照的维修工单直接办结） | `PROCESSING` | `COMPLETED` |
| REJECT（调度驳回） | `PENDING_DISPATCH` / `ASSIGNED` | `REJECTED` |
| CANCEL（随申请撤销） | `PENDING_DISPATCH` / `ASSIGNED` / `PROCESSING` / `ONSITE_PHOTO_RECORDED` / `PENDING_CONFIRMATION` | `CANCELLED` |

规则：

- 派单对象必须持有启用状态的 `WORKER` 角色并处于启用账号。
- 只有 `REPAIR` 申请在同一事务内创建唯一维修工单（`uk_work_order_request`）；非维修申请的学生/通用详情 `workOrder=null`。
- 维修队列、负载、SLA 统计及派单/处理入口只接受 `flow_type=REPAIR` 且未归档的工单；历史非维修记录即使传入工单 ID 也不得继续派单。
- 首次派单将申请从 `SUBMITTED` 推进到 `PROCESSING`，改派不重复推进。
- 报修类工单按显式目录配置使用 `photo_workflow_required=1` 时，不允许直接 `COMPLETE`，必须先现场拍照、再上传完工照片并提交确认。
- 完工照片支持多张（`completion_photo_file_ids` 保留历史，`completion_photo_file_id` 为最新一张）；现场与完工照片均校验上传者本人才可使用。
- 报修人退回时记录 `confirmation_reject_reason` 并通知服务人员重新拍照；工单列表按 `PROCESSING` 筛选时同时覆盖 `ONSITE_PHOTO_RECORDED` 与 `PENDING_CONFIRMATION`。
- 宿舍报修表单对齐学校官方报修应用字典（V47）：报修类型 12 类（门窗/墙皮/地砖/桌子/椅子/床/风扇/空调/灯/停电/停水/漏水），宿舍楼为 4 社区 21 栋的单选（`dormBuilding`）+ 房间号（`address`）。工单创建时 `faultType` 命中停电/停水/漏水自动置 `priority=URGENT`，其余为 `NORMAL`；详情里的报修地址由「宿舍楼 + 房间号」拼接。

## 权限与数据范围

| 动作 | 功能权限 | 数据范围 |
|---|---|---|
| 提交/查看/撤销本人申请 | `service-request:create` / `service-request:view:self` | 仅本人（资源归属校验） |
| 调度队列、派单、驳回 | `work-order:dispatch` | 角色绑定组织的 `ORGANIZATION_AND_CHILDREN` 子树，`ALL` 放开 |
| 查看/处理被指派工单 | `work-order:view:assigned` / `work-order:process` | 仅被指派人 |
| 现场/完工拍照 | `work-order:process` | 仅被指派人，且照片必须本人上传 |
| 报修人确认/退回 | `service-request:view:self` | 仅该申请本人 |
| 提交评价 | `evaluation:create` | 仅维修申请本人，仅 `COMPLETED`，一次 |
| 请假审批/销假、人工受理/办结 | `platform:all` / `catalog:manage` / `work-order:dispatch`（沿用现有边界） | 当前管理校区、组织数据范围 |
| AI 会话 | `ai:chat` | 仅本人会话 |

## 幂等与单号

- 提交申请支持 `Idempotency-Key` 请求头，`(requester_id, idempotency_key)` 唯一约束兜底；重复提交返回首次创建的申请。
- 单号规则：`SR-yyyyMMdd-{id}` / `WO-yyyyMMdd-{id}`，`id` 为雪花 ID，天然唯一。
- 全局 Long 序列化为字符串（`JacksonConfig`），雪花 ID 在小程序端无精度丢失。

## 通知触发点

| 事件 | 通知对象 |
|---|---|
| 提交成功 | 申请人；文案按维修待派单/请假待审批/人工待受理区分 |
| 请假批准/驳回/销假、人工办结 | 申请人，关联 `SERVICE_REQUEST` 与本申请 ID |
| 催办 | 已派维修提醒服务人员；未派维修/请假/人工事项提醒实际有权限且在受理范围内的人员；无人可通知则如实返回已记录催办 |
| 派单 | 被指派服务人员；首次派单同时通知申请人 |
| 开始处理 | 申请人 |
| 提交完工照片待确认 | 申请人（引导确认） |
| 报修人确认办结 | 被指派服务人员 |
| 报修人退回 | 被指派服务人员（引导重新拍照） |
| 办结 | 申请人（引导评价） |
| 驳回 | 申请人 |
| 撤销 | 被指派服务人员（如已派单） |
| 评价 | 被评价的服务人员 |

## AI 助手约定

- 系统提示词由后端版本化（`CampusAssistantPrompts.PROMPT_VERSION`），客户端不可覆盖。
- 每用户每小时消息数限流（默认 20，`AI_CHAT_HOURLY_MESSAGE_LIMIT`），超限返回 `AI_429_01`。
- AI 未配置或调用失败时返回降级回复并落库 `FAILED` 状态消息，不中断会话。
- 消息落库记录模型、提示词版本、token 用量与耗时，用于审计。
