## 一、项目定位与目标客户

### 1.1 一句话定位

**Student Hub 是一套面向单校区的“校园服务大厅 + 办事工单闭环 + 校园社区 + AI 助手 + 数据大屏”的轻量校园服务中台，不是教务系统替代品。**

它真正卖的不是“又一个校园 App”，而是三件事：

1. **把线下办事变成可追踪的工单**：学生提交 → 自动建单 → 调度派单 → 师傅现场/完工拍照 → 学生确认 → 评价 → 管理端看板；全链路留痕、可催办、可考核。
2. **把学校自己的信息与社区运营起来**：官网通知自动抓取、官方号发布、分区/话题/举报/申诉/屏蔽词治理，数据留在学校自己的服务器。
3. **把 AI 做成“有业务上下文”的助手**：课表、申请进度、办事指南、校内知识库问答，而不是一个只会聊天的壳。

### 1.2 目标客户（按角色）

| 角色 | 诉求 | 当前满足度 | 说明 |
|---|---|---|---|
| **学生**（核心用户） | 课表/成绩、报修/请假/证明、消息通知、社区交流、AI 问答 | **中高**（课表/成绩需绑定真实教务账号；社区与工单真实） | App + 微信小程序两端；首页 BFF、统一收件箱、勋章成长体系已具备 |
| **后勤服务人员 / 维修工** | 接单、现场拍照、完工提交、电话联系报修人 | **高** | 工单全流程、现场/完工拍照、报修人确认/退回是当前最完整的能力 |
| **后勤调度 / 部门负责人** | 派单、改派、驳回、看时限、看数据 | **中** | 派单/驳回/数据范围真实；**无 SLA 超时升级、无工时/物料/成本、无排班** |
| **辅导员 / 教师** | 请假审批、班级事务、作业、通知到人 | **低—中** | 教师仅有教务身份标识；无教师工作台/班级管理/审批链；作业中心已有“发布→学生提交→关闭”最小闭环，但仍无教师侧入口、附件、评分/批改 |
| **学校管理者（校领导/信息中心）** | 一站式服务、数据看板、可私有化、合规可控、可复制 | **中** | 有真实工作台、大屏、权限/组织/角色、社区治理；但**缺生产初始化、统一身份、审计、推送、SLA 报表、合规材料** |
| **宣传 / 团委 / 学工** | 通知触达、社区运营、舆情治理 | **中高**（社区运营强，通知触达弱） | 官方号 + 官网通知抓取 + 举报/申诉/处罚/屏蔽词真实；**新通知不推送、无内容日历、无匿名、无全局搜索** |

### 1.3 最适合的首批客户画像

- 单校区民办本科 / 高职 / 中职，5,000–20,000 学生；
- 教务使用**青果（Kingosoft）**、官网为可抓取的静态新闻站（当前代码即按绵阳城市学院适配）；
- 有微信生态诉求（小程序为主），无自建 App 团队；
- 信息中心 1–3 人，预算 10–30 万/年，采购决策链短（民办校 1–2 个月可启动）；
- 痛点明确：报修靠电话/微信群、通知靠辅导员转发、数据靠 Excel、社区靠 QQ 群。

**首批标杆建议就是绵阳城市学院本身**（代码/域名/青果/官网均已按该校适配），做成可写进合同的验收案例后，再复制同省同类民办校。复制时的主要成本不在业务代码，而在**教务适配 + 学校身份/组织初始化 + 文案品牌替换**。

### 1.4 不适合（或需大改后）才适合的客户

- 双一流 / 多校区大学：需要统一身份（CAS/OAuth）、等保三级、招投标、强多租户隔离，当前不具备；
- 需要完整教务（选课、考试、评教、学籍）或缴费/一卡通闭环的学校：本产品明确不做教务替代，支付能力为零；
- 要求“应用商店上架 + iOS + 鸿蒙 + 等保测评报告”同步交付的客户：当前只有 Android debug 包，iOS/鸿蒙与合规材料需另立项目。

### 2.2 教务课表与成绩（真实，但绑定单校）

**已经具备**

- 教务认证：青果 SSO + 算术验证码 + RSA 加密密码；**账号密码不落库**，只加密托管短期教务 Session（AES-GCM + Redis，默认 48h）；失效置 `EXPIRED` 要求重新认证（`modules/jwauth`、`integration/jw/KingosoftJwClient`）。
- 课表：`POST /api/app/schedule/import`、`GET /view`、`GET /view-week`、`GET /next-course`、`GET /adjustments`；服务端周展开（节次→时间映射）、单双周、班级课表缓存兜底、调课公告采集与定向通知（`modules/schedule`，定时同步 cron `0 0 7-21/2 * * *`）。
- 成绩：`GET /api/app/grades` 实时读取教务「学业成绩」页，按学期分组，含 GPA/平均分/加权平均分/有效成绩与原始成绩区分，5 分钟缓存（`modules/grades`、`integration/jw/KingosoftGradesClient`）。
- 身份联动：教务认证成功后可自动切换平台身份 STUDENT / TEACHER（`JwAuthServiceImpl`）。

**演示 / Mock 边界**

- 本次运行实例用开发账号 `requester` 测试：`GET /api/app/schedule/view` 返回空课表，`GET /api/app/grades` 返回 `JW_401_02`（未绑定教务）。**教务相关演示必须先准备一个真实青果测试账号**，否则只能演示“去认证”空态。
- App 成绩页在接口失败时会进入 `_demoMode`，显示“教务认证不可用，当前展示示例数据”（`app/lib/pages/schedule/grade_query_page.dart`）——这是**明确标注的示例数据**，可用于视觉演示，但不能当作真实业务数据。

**商业化限制（必须对客户讲清楚）**

- 所有教务 URL、CAS service、RSA 公钥、域名都按绵阳城市学院写死在 `JwProperties` / `OfficialSiteClient` 默认值中；**换一所学校必须做适配与联调**，不是改配置就行。
- 依赖教务 HTML 页面结构（青果版本差异会破坏解析）；没有正式 API 授权时存在**合规与稳定性风险**，必须由学校书面授权并明确“代查”边界。
- 只有课表 + 成绩；**没有考试、选课、学籍、评教、考勤**。教师侧只有身份标识，无教师工作台。
- 不适合在合同里承诺“教务实时可用”，应写成“在教务系统可访问且学校授权的前提下提供查询，上游故障时明确提示”。

### 2.6 服务工单（真实，当前最成熟）

**已经具备**

**演示边界**：开发库有 3 条不同状态申请 + 2 张工单，配合 `requester` / `worker` / `dispatcher` / `admin` 四个账号可完整演示。**这条链路是当前最值得放在销售首屏的能力。**

**商业化缺口**

### 2.7 AI 助手（代码完整，但当前不可真实调用）

**已经具备**

- `AiProvider` 抽象 + OpenAI-compatible 适配（3 种协议：OPENAI_CHAT / ANTHROPIC_MESSAGES / OPENAI_RESPONSES），管理端可配供应商/模型/默认模型、连通性检查、远端模型导入。

- RAG：知识库管理、文档上传/重建索引、混合召回（向量 + `pg_trgm` 词法，RRF 融合），可注入 App AI 上下文；上下文预算与历史压缩（V58）。
- 业务上下文：课表/下一节课、申请进度、服务目录、办事指南等意图与动作卡片（`AiAssistantDataServiceImpl`）；每用户每小时 20 条限流；模型失败降级回复。

**当前不可真实演示的原因（已验证）**

- `GET /api/admin/ai/providers`：默认供应商 `enabled=false`、`apiKeyConfigured=false`；

- RAG 依赖独立 PostgreSQL（README 要求），本地 `docker-compose.yml` 未包含该服务；
- `.env` 中 `AI_ENABLED=false`（以数据库运行时配置为准，但供应商未启用）。

**商业化缺口**：无内容安全审核（输入/输出）、无人工转接、无按学校/租户的配额与成本计量、无模型 Key 托管方案、无 AI 审计导出；RAG 的 PostgreSQL/pgvector 是额外运维组件。

| 缺口 | 现状 | 商业影响 |
|---|---|---|
| 学校统一身份认证（CAS/OAuth2/企业微信/钉钉） | 只有青果 SSO + 微信/QQ；平台登录无学校 SSO | 大型/公办校无法采购；学生身份无法与学籍名单强绑定 |
| 生产管理员登录 | 生产关闭密码登录，无替代登录方式 | **部署后管理台打不开**，验收无法进行 |
| 学校/校区/组织/管理员初始化 | **已有迁移级修复（V2_1 + out-of-order），待全新 MySQL 空库验收**；生产管理员账号/SSO 仍缺 | 空库是否可完整部署待验收；生产管理员入口仍不可用 |
| 学生/教师名单导入与实名核验 | 无导入、无学号唯一校验（仅教务绑定后可获得学号） | 无法防非本校人员；数据上报口径不可信 |
| 账号生命周期 | 无注销、无数据导出、无毕业离校处理 | 个人信息保护合规风险；学校年复一年使用会积累脏数据 |
| 多校区/多学校 | 表有 `campus_id`，但无校区管理、无租户隔离、无按校配置 | 只能一校一套部署，复制成本高 |

### 3.2 作业 / 课程 / 教学（P1，影响“教师/教务”客户）

- 作业中心已具备“管理员代发（教师暂无发布入口）→ 学生列表/详情/提交（覆盖、截止/关闭校验）→ 关闭”的最小闭环，但不能等同于完整作业平台：**无教师工作台、无附件、无评分/批改/退回、无通知、无统计**；管理台作业页已注册（静态 200，待浏览器复验）。
- 没有考试安排、成绩发布提醒、选课、考勤、评教；
- 没有教师工作台（发布作业、看班级、审批请假、发通知）；教师目前只是“能登录的学生端 + 身份标识”；
- 结论：**不要把“教学平台”写进销售承诺**；首期只卖“教务数据查询（课表/成绩）+ 事务办理 + 作业最小闭环”，教师侧作为后续增值。

### 3.3 运营工具（P1）

- 公告/通知管理页面缺失（后端有 API），运营无法在界面发公告；
- 无推送、无内容日历、无定时发布（公告表有 SCHEDULED，但 UI 未消费）、无灰度/定向；
- 无全局搜索/热搜、无匿名发帖、无 @ 提及、无话题运营位；
- 无运营周报/月报导出、无举报处置时效看板、无内容巡检；
- 无法把“官网通知抓取”自动转成“推送 + 首页卡片 + 未读”（目前只发社区帖）。

### 3.4 数据分析（P1）

- 现有管理台工作台：待处理工单、今日新增用户、今日 AI 会话、待受理申请、7 天工单趋势、分类占比、最新工单——**数字真实，但维度少**；
- 缺：服务满意度（NPS/好评率）、SLA 达成率、平均办结时长、超时 TOP、部门/师傅绩效、申请漏斗（提交→派单→办结→评价）、社区留存/互动率、通知到达率、AI 使用与成本；
- 无报表导出、无定时邮件/周报、无按组织/校区钻取；
- 大屏内容含 8 条演示公告（V35），客户交付前必须替换。

### 3.5 付费 / 账单（P2，但影响商业模型）

- 项目内**完全没有支付、账单、充值、订阅、配额、许可**能力；
- 电费只有只读查询，无充值；服务工单无收费项；
- 这意味着：**不能按交易抽成、不能做校园缴费、不能做 SaaS 订阅计费**；短期只能按“项目 + 学年服务费”收费（见 §4）；
- 若未来要做“平台使用费/按学生数计费”，需要补 license/租户/用量计量（当前 AI 有 token 用量记录但未聚合计费）。

### 3.6 通知触达（P0/P1，影响 SLA 与紧急通知）

- 站内 + WebSocket 只能覆盖“正在使用 App 的人”；
- 没有 OS 推送（FCM/APNs/厂商通道）、微信订阅消息、短信、邮件；
- 后果：报修超时提醒、派单提醒、成绩发布提醒、紧急停水停电通知、社区处罚通知都无法真正“触达”；
- 学校最容易验收的一条就是“通知能不能到手机”，当前答不上来。**这是首期必须补的能力，优先级高于作业/电费。**

### 3.7 SLA（P1，影响后勤采购理由）

- 服务项 `slaHours` 只有展示；工单无 deadline 字段、无超时扫描、无升级、无免责/延期、无达成率统计；
- 催单只有 2 小时冷却，不解决“没人处理”；
- 管理端“即将超时 17 件”是设计稿样例，不是真实数据；
- 后勤处采购最关心的“24 小时办结率”目前**无法出具报表**。

### 3.8 学校侧部署与合规（P0）

| 缺口 | 现状 |
|---|---|
| 生产初始化与升级 | **空库迁移已有 V2_1 + out-of-order 迁移级修复，待全新 MySQL 空库验收**；生产管理员 bootstrap（账号/SSO）仍缺；无升级/回滚脚本、无备份恢复脚本、无数据迁移演练 |
| 可观测性 | 只有 `/actuator/health`；无 Prometheus 指标、无结构化日志配置、无告警、无日志轮转 |
| 容器化 | Dockerfile 可用；compose 仅 dev（mysql/redis/api，无 MinIO/PostgreSQL、无 healthcheck/restart/资源限制）；**上传文件未挂载卷，容器重建即丢** |
| 安全默认值 | `FILE_SIGN_SECRET`、`JW_ENCRYPT_KEY` 有 dev 默认值，prod 不强制覆盖；QQ 默认 mock；邮件验证码返回 devCode；App 启动自动 dev 登录/mock 会话；release 用 debug 签名 |
| 合规材料 | 无 LICENSE、无隐私政策/用户协议、无 ICP/等保/数据分类分级说明、无个人信息收集清单、无数据保留/删除策略、无审计 |
| 校方授权 | 教务代查、官网抓取、电费第三方数据都需学校/第三方书面授权；当前无授权模板/DPA |
| 多端交付 | 微信小程序与 Flutter App 两套客户端功能/信息架构不一致；无发布流程文档 |

## 四、产品分层、定价与试点路径

> 说明：以下价格为**建议区间（人民币，含税与否需在合同中明确）**，基于单校区 8,000–20,000 学生的民办/高职市场估算；最终需按学校预算、采购方式（直采/招标）、部署方式（公有云/私有化）确认。不含硬件、带宽、短信、模型 token、等保测评、微信认证等第三方费用。

### 4.1 分层原则

1. **按“校区 + 学年/学期 + 模块组合”报价**，不按人头（学校对“按学生数收费”普遍敏感）；
2. **实施费单列**（首年一次性），试点转正式可抵扣；
3. **教务/身份/推送是加价项**，因为它们需要学校配合与适配成本；
4. **AI 单列用量包**（模型 token 由客户提供 Key 或我方代管，成本另计）；
5. **SLA 与运维托管单列**，避免“承诺了 99.9% 却没有运维人力”。

### 4.2 套餐设计（可直接用于报价单）

| 套餐 | 适用对象 | 包含内容 | 部署 | 服务 | 建议价（区间） | 计价单位 |
|---|---|---|---|---|---|---|
| **L0 演示包** | 售前 | 演示环境 + 4 个演示账号 + 服务目录/工单/社区/大屏/AI 配置页（AI 降级） | 我方环境 | 1 次线上演示 + 1 份方案 | 0–1 万（可抵扣后续合同） | 次 |
| **L1 试点版** | 单个部门（后勤/学工），1 个校区 | 服务大厅 + 报修/事务工单 + 消息中心 + 社区基础（发帖/评论/举报）+ 管理台（目录/工单/用户/看板）+ 部署 + 培训 | 学校私有云或我方云 | 8×5 响应；1 次数据初始化；2 场培训 | **3–6 万 / 学期**（实施费 1–2 万单列） | 学期 / 校区 |
| **L2 标准版** | 单校区全校 | L1 + 教务课表/成绩（需学校授权）+ 学校身份对接（CAS/OAuth 或微信+学号核验）+ 通知推送 + 公告管理 + 社区治理完整版 + 数据看板 + 审计日志 + 小程序/App 发布 | 私有化（推荐）或专属云 | 5×8 响应；每学期 1 次巡检；培训 3 场；SLA 99.5% | **12–20 万 / 学年**（实施费 3–5 万单列） | 学年 / 校区 |
| **L3 专业版** | 多校区 / 集团校 / 有等保要求 | L2 + 多校区租户、统一身份网关、审批流定制、SLA 考核与报表、开放 API、等保测评配合、专属运营顾问 | 私有化 / 混合云 | 7×12 响应；季度巡检；专属客户成功 | **25–50 万 / 学年**（实施费 5–8 万单列） | 学年 / 学校（含 2 校区，超出每校区 +6–10 万） |

### 4.3 可执行套餐项（模块 SKU，用于组合报价）

| SKU | 内容 | 建议年费（参考） | 备注 |
|---|---|---|---|
| 服务大厅 + 申请工单 | 目录、动态表单、申请、派单、工单、拍照、确认、评价、催单 | 4–6 万 | 必选，价值最容易被验收 |
| 消息与公告 | 站内通知、收件箱、公告管理、偏好 | 1–2 万 | 不含推送通道 |
| 社区 + 治理 | 分区/话题/发帖/评论/举报/申诉/处罚/屏蔽词/官方号 | 3–5 万 | 建议含运营培训 |
| 教务基础包 | 教务认证、课表、调课、成绩 | 5–8 万 | 含 1 次学校适配；换校重新报价 |
| 统一身份/组织包 | CAS/OAuth 对接、组织/用户导入、数据范围配置 | 3–5 万 | 依赖学校提供接口文档与测试环境 |
| 通知触达包 | 微信订阅消息 / 厂商推送 / 短信（用量另计） | 2–4 万 | 首期建议至少接微信订阅消息 |
| AI 助手包 | 模型接入、RAG 知识库、推荐问题、SSE | 2–4 万 + token 成本 | 模型 Key 客户提供或代管；RAG 需 PostgreSQL |
| 数据大屏 / 终端 | 大屏页面、现场终端、单号查进度 | 1–2 万 | 内容需客户提供 |
| 作业中心（最小闭环） | 管理员发布/关闭、学生列表/详情/提交（覆盖、截止/关闭校验） | 2–3 万 | 无教师侧/附件/评分，按“最小闭环”报价；完整版另计 |
| App / 小程序发布包 | 品牌替换、打包、上架辅导、版本发布 | 0.5–1 万 | iOS/鸿蒙另计 |
| 运维托管 / SLA | 监控、备份、升级、巡检、应急 | 2–4 万/年 | 与 L2/L3 服务等级联动 |
| 定制开发 | 服务目录/审批流/报表/对接 | 0.5–3 万/项 | 按人天报价，建议 1,500–2,500 元/人天 |

**组合示例（单校区民办本科，10,000 学生）**：
L2 标准版 16 万/学年 + 实施 4 万 + 通知触达 3 万 + AI 2 万 = **首年约 25 万**；次年续费约 18–20 万（不含新增定制）。若只做后勤试点：L1 4 万/学期 + 实施 1.5 万 = **首学期 5.5 万**。

### 4.4 合同与付款建议

- **试点对赌**：以“报修平均办结时长下降 30% / 超时率 <10% / 满意度 ≥4.5 / 月活 ≥60% 在校生”中的 2–3 项作为验收条件，未达标延长服务期或退部分费用；
- **付款节点**：3:4:3（签约 / 上线试运行 / 学期验收）；
- **续费**：次年按 85–90% 续费；新增模块按 SKU 补差；
- **数据归属**：合同明确数据归学校所有，我方仅在授权范围内处理；到期导出并删除；
- **合规责任**：学校负责统一身份/教务/官网/电费数据授权，我方负责系统安全与运维；等保测评由学校牵头、我方配合。

### 4.5 试点路径（从 0 到续费）

| 阶段 | 周期 | 动作 | 目标 / 验收 |
|---|---|---|---|
| ① 演示 | 1–2 周 | 用 L0 演示包讲“报修闭环 + 社区治理 + 大屏”，现场用演示账号走一单 | 拿到试点意向与对接人 |
| ② 部门试点 | 1 个学期（约 4 个月） | 选后勤处（报修）或学工处（通知/社区）单点上线；初始化组织/用户；培训 2 场；每周运营例会 | 工单闭环率 ≥90%，平均办结时长有基线对比，满意度 ≥4.5 |
| ③ 扩面 | 1–2 个月 | 加消息/公告/社区/教务（如学校授权）；上线管理台看板与月报 | 覆盖 2–3 个部门，月活 ≥50% |
| ④ 学期验收 | 学期末 | 按对赌指标出验收报告 + 数据月报；签学年合同 | 转 L2 标准版，续费 |
| ⑤ 复制 | 下一学年 | 换校适配清单（教务/身份/官网/品牌/初始化），目标 4–6 周交付第二所 | 单校交付成本下降 30% |

## 六、结论与建议决策

1. **定位收敛**：对外只讲“校园服务中台 + 工单闭环 + 社区治理 + AI 助手”，教务只讲“课表/成绩查询（需学校授权）”，不讲“教务替代/教学平台”。这是当前代码真实支撑得住的最大叙事。
2. **首单打法**：以**后勤报修**为切口（价值最直观、验收最容易），1 个学期试点，对赌“办结时长/超时率/满意度”，再扩到学工/社区/通知。不要首单就承诺教务、支付、统一身份全套。
3. **先修交付基线，再谈功能**：第 1–2 周必须完成提交基线、测试修复（V62）、**空库迁移验收（V2_1 + out-of-order 已有迁移级修复，需用全新 MySQL 空库跑通 V1–V65）**、生产管理员 bootstrap/SSO、安全开关、演示数据隔离；管理台 `RolesPage/OrganizationsPage/HomeworkAdminPage` 三页已注册（静态 200），交付前做一次浏览器逐页复验，否则任何客户 POC 都会在“装不起来/登不进去/页面空白/测试是红的”上翻车。
4. **把“通知触达”和“SLA”当成首期必做项**，而不是作业/电费。它们直接决定后勤/学工是否愿意付费，也是竞品（只读教务代理）无法提供的差异。
5. **商业模型**：首年“项目实施费 + 学年订阅 + 模块 SKU”，第 2 年起靠续费与增值（身份/推送/AI/报表）；支付与交易抽成在 12 个月内不碰。
6. **风险披露**：教务代查、官网抓取、电费第三方数据都需要学校/第三方授权；当前无隐私政策/用户协议/审计/等保材料，**在补齐合规包之前不应进入正式生产**，只适合试点/内测。
