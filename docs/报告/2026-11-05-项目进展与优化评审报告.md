## 3. 建议优先处理的问题

### P1：按账号、校区与查询隔离信息流快照

证据 E-03：`app/lib/services/community_feed_cache.dart:13` 使用唯一全局键；`app/lib/api/community_api.dart:120` 将所有分区、排序的第一页写到同一位置；`app/lib/api/auth_service.dart:26` 的账号清理没有处理信息流缓存。

影响：同设备切换账号、服务地址或校区后，可能显示上一份帖子和个性化互动状态；最后浏览某个分区后重启，也可能先把该分区内容放进默认信息流。网络失败时旧内容会继续保留。空列表还会被 `saveRawRecords` 直接跳过，已失效快照没有被更新。

建议：缓存元数据绑定服务地址、账号、校区、分区和排序；增加保存时间、有效期及空结果覆盖策略；退出或账号切换时清理对应缓存。异步恢复完成后应主动通知 UI：当前 `_restoreFeedSnapshot` 只调用 `seed`，而 `seed` 没有通知监听者，显示时机依赖其他重建，应补慢网场景验收。

验收：A 账号缓存对 B 账号不可见；切校区或筛选不串数据；空结果清掉旧内容；分区请求延迟时快照仍可独立显示。

### P1：补全分享的冷启动、登录与网页承接

证据 E-04：`app/lib/main.dart:70` 在 `runApp` 前启动深链监听；`community_deep_link_service.dart:64` 在 Navigator 尚未创建时直接返回，`:69` 在未登录时直接返回；现有深链测试只验证 URI 解析和链接拼装。

影响：冷启动链接在导航就绪前到达时会丢失；未登录打开链接后，登录也没有待办链接可继续。请求过程中若退出或换号，返回后也没有校验原会话，可能继续导航并使用新的账号 store。

建议：入口尽早接收链接，保存待处理目标，在首帧及会话就绪后消费；处理过程绑定会话代数，加入去重和错误反馈。部署侧补齐或核验 `/.well-known/assetlinks.json`、签名指纹与 `/c/{slug}` 网页承接，覆盖已安装、未安装、未登录、冷启动和热启动。

仓库部署目录未检索到 assetlinks 与分享网页承接配置。本机对两个公开地址的只读请求均在 TLS 握手阶段失败（curl exit 35、HTTP 000），因此线上是否已另行配置仍待核验，本文不据此断言线上 404。

### P1：恢复稳定的 App 全量回归并建立自动检查

证据 E-02：本次实际失败、QQ 挂起和静态分析结果；仓库未见 `.github/workflows` 或其他已提交的常见 CI 入口。

建议：先修会话测试输入与实际 `AUTH_401` 契约的差异；版本断言改从构建配置取得期望值；单独处理 QQ 测试的异步资源释放和超时；复核页面文案断言与课表溢出。随后把后端测试、Flutter 全量、Dart 分析、管理端资源校验纳入持续集成，静态提示先按基线禁止新增，再逐步归零。

验收：全量测试能在明确时间内自行结束，功能失败数为 0；网络、插件和 WebSocket 测试使用可控替身；每次合并均保存检查结果。

### P1：将计数一致性扩展到评论和其他写入路径

证据 E-05：`CommunityServiceImpl.java:290` 的评论数仍读取旧值后 `updateById`，且没有检查更新行数；`:384` 删除评论仍修改整份帖子实体。治理状态切换也存在整实体写回。新点赞 SQL 则直接更新计数、不增加实体版本。

影响：并发评论可能已经写入，但评论总数只增加一次；其他路径写回旧帖子实体时，还可能覆盖刚更新的点赞值。现有 `CommunityLikeCountIntegrationTest` 覆盖的是顺序点赞/取消，尚未覆盖真实并发和交错写入。

建议：评论计数改为原子增减；其他状态操作仅更新所需列，统一计数和版本策略；在贴近生产的 MySQL 环境验收并发评论、删除与点赞交错，以及同账号多端重复操作。计数应与有效明细条数一致。

### P2：下一轮性能优化优先落到图片传输与数据库聚合

证据 E-06：自然帖子列表裁剪了 `thumbnailUrls`，保留完整 `imageUrls`；客户端 `mapPost` 使用后者，卡片 `Image.network` 仅设置 `cacheWidth`。这可以减少解码内存，网络仍传输原图。

建议：列表下发适配预览尺寸的图片地址或缩略图，详情再取原图；避免在列表请求期间首次同步生成缩略图。用弱网首图时间、每屏图片下载字节数、缓存命中率评估收益。

作者等级批量计算已经消除了逐人查询，但 `AchievementService.java:204` 后仍拉取这些作者的历史帖子、评论、申请等明细，在 Java 中计数。随着历史数据增长，可改数据库 `GROUP BY` 聚合，之后按实测决定是否增加汇总表或缓存。点赞响应也可收敛为帖子 ID、点赞状态和计数，减少整帖、图文块、图片签名与等级重算。

### P2：补评论分页，控制大文件维护成本

证据 E-07：服务端详情固定按时间升序取前 100 条评论；客户端在这批数据上切换最热/最新。评论超过 100 条时，“最新”只能看到前 100 条中的最新项，新增内容重新进入详情后可能看不到。

建议：独立评论分页接口，服务端支持排序、稳定游标和楼中楼分页；帖子详情首屏只取必要评论。随后沿请求状态、评论操作、正文渲染拆分 `post_detail_page.dart`（1740 行）和 `home_page.dart`（1489 行），保留现有布局与互动回归。
