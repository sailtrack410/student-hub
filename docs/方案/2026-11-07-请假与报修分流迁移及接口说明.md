# 请假与报修分流：迁移及接口说明

更新日期：2026-11-07。本文说明第一阶段代码的接口和迁移口径；动态验证结果单独记录在 `artifacts/service-flow-20261107/VERIFICATION.txt`，不能将接口设计当成测试通过记录。

## 流程配置与已有事项

`service_item.flow_type` 为明确配置，服务目录管理端、管理接口及 App 目录接口使用 `flowType` 字段。合法值为 `REPAIR / LEAVE_APPROVAL / MANUAL / GUIDE`。新建默认 `MANUAL`；无配置、未知类型不得自动派维修工单。表单名称不参与流程判定。请求创建时保存流程类型与事项编码快照，目录后续变更不改写已有申请的流程。

V109 核对的是仓库已有基线事项，按精确编码一次性初始化：

| 事项编码 | 流程 | 第一阶段实际能力 |
|---|---|---|
| `REPAIR-DORM`、`REPAIR-PUBLIC` | `REPAIR` | 维修派单、处理、照片、验收、退回及评价 |
| `AFFAIR-LEAVE` | `LEAVE_APPROVAL` | 管理端审批、驳回、销假 |
| `AFFAIR-VENUE`、`CERT-ENROLL` 及其他未明确配置事项 | `MANUAL` | 有权限人员受理、记录线下结果并办结 |
| `GUIDE-CONSULT` | `GUIDE` | 阅读说明与指南，不接收通用申请 |

场地预约冲突、资源占用、自动电子出证、证明下载和教师/辅导员关系集成均未包含在本阶段。已存在的学校文案不能作为这些功能已接通的证明。

管理端目录保存 `flowType`；只有 `REPAIR` 可以配置维修拍照流程。复制事项保留其流程配置并按原规则生成停用副本，管理员确认后上架。

## 学生与管理端契约

旧 `status`、申请 ID、通用表单和维修工单响应结构保留。学生与管理端通用申请摘要/详情增加 `flowType / itemCode / businessStatus / statusLabel / availableActions`，详情按用途补充请假数据与办理意见。独立请假列表也提供 `businessStatus / statusLabel / availableActions`，原有 `leaveStatus` 保留兼容。字段口径如下：

| 字段 | 说明 |
|---|---|
| `flowType` | 申请创建时保存的流程类型 |
| `itemCode` | 事项编码快照 |
| `businessStatus` | 根据实际业务表达的状态；不替换通用 `status` |
| `statusLabel` | 与该申请业务一致的用户可见状态 |
| `availableActions` | 当前用户与业务状态下实际可执行动作；前端不得仅凭状态显示按钮 |
| `leaveType / leaveStartAt / leaveEndAt / leaveDays` | 学生申请详情及独立请假接口的请假专属数据 |
| `approvalComment` | 申请详情及独立请假详情的最近审批/受理意见，和时间线保留记录配合使用 |
| `leaveCancelAt` | 学生申请详情及独立请假接口的销假时间；`leaveStatus=CANCELLED` 是旧兼容值，不能单独区分已销假与已撤回 |
| `workOrder`、工单摘要字段 | 非报修为 `null`；历史错误工单不会被作为当前业务流程返回 |

学生端请假详情展示起止、天数、审批意见、销假结果及时间线，不显示维修师傅、维修地址、维修照片、确认完工或维修评价。销假由管理端执行，学生端不新增销假按钮。列表与详情共用 `flowType / statusLabel / availableActions`；返回空动作数组即不展示业务操作。旧服务端缺少新增字段时可保留兼容显示，有明确 `flowType` 时不得回落到错误维修页面。

请假的 `businessStatus` 为 `PENDING_APPROVAL / APPROVED / CLOSED / REJECTED / CANCELLED / COMPLETED`。其中 `CLOSED` 表示有销假时间的已销假，`CANCELLED` 表示学生已撤回；历史 `status=COMPLETED` 且无销假时间时保留 `businessStatus=COMPLETED / statusLabel=已办结`，不伪造销假。人工事项提交后为 `PENDING_ACCEPTANCE`，受理后为 `PROCESSING`，办结后为 `COMPLETED`。维修有有效工单时使用工单状态。学生请假待审批时仅有 `CANCEL / URGE`，已批准后无学生办理动作；管理端销假的独立接口动作仍为 `CANCEL`，时间线事件为 `LEAVE_CANCEL`。

管理端请假列表与详情优先显示 `statusLabel`，缺失时结合 `businessStatus`、通用 `status` 和销假时间回退。筛选使用 `WITHDRAWN` 区分已撤回、`COMPLETED` 查询历史已办结，原 `CANCELLED` 筛选用于有销假时间的已销假。列表与详情均以 `availableActions` 显示业务操作；空数组表示无操作，只有响应缺失该字段时才兼容原状态判断。已撤回、已销假和历史已办结记录均无办理动作。

### 端点与动作

| 端点 | 行为 |
|---|---|
| `POST /api/app/service-requests` | `REPAIR` 才建维修工单；请假入审批，其他可提交事项入人工受理；`GUIDE` 拒绝提交；继续支持 `Idempotency-Key` |
| `GET /api/app/service-requests`、`/{requestId}` | 只读本人，返回业务状态、可执行动作及请假信息 |
| `POST /api/app/service-requests/{requestId}/cancel` | 按类型与状态撤回，不为请假额外创建或处理维修工单 |
| `POST /api/app/service-requests/{requestId}/urge` | 按实际接收人返回催办结果，无可通知人员时返回已记录催办；保留冷却期 |
| `POST /api/admin/leave-requests/{requestId}/approve` | `{comment}`；请假审批通过，时间线动作 `APPROVE`，通用状态 `SUBMITTED → PROCESSING` |
| `POST /api/admin/leave-requests/{requestId}/reject` | `{reason}`；请假驳回并通知申请人 |
| `POST /api/admin/leave-requests/{requestId}/cancel` | `{comment}`；管理端销假，时间线动作 `LEAVE_CANCEL`，`PROCESSING → COMPLETED` 并记录销假时间 |
| `POST /api/admin/service-requests/{requestId}/review` | `{action: "APPROVE"或"REJECT", comment}`；人工受理/驳回；请假复用独立审批逻辑，维修不走此入口 |
| `POST /api/admin/service-requests/{requestId}/complete` | `{comment}`；只对已受理 `MANUAL` 申请人工办结，不创建维修工单 |

管理端保留现有 `platform:all / catalog:manage / work-order:dispatch` 权限边界及管理校区/组织数据范围。学生对他人申请、无权限账号审批、超范围管理、终态重复办理均由服务端拒绝；前端按钮隐藏不能代替服务端验证。

服务申请页按业务状态显示。请假行进入 `#/leave?requestId=...`，直接打开原有独立请假详情；维修由维修调度页处理；人工事项使用服务端返回的 `APPROVE / REJECT / COMPLETE` 动作。维修队列、SLA 与负载统计排除非维修及归档记录。

通知继续使用 `relatedType=SERVICE_REQUEST / relatedId=申请ID` 定位；不同类型打开同一申请详情后由业务契约决定呈现。审批、销假、驳回及终态不应被“仅处理中”筛选截断。催办文案使用服务端真实结果，不统一显示提醒师傅。

## V109：历史工单修复

迁移文件：`src/main/resources/db/migration/V109__separate_service_request_flows.sql`。本阶段使用 Flyway 新迁移，不修改已应用迁移，也不覆盖整库。

1. 为目录增加 `flow_type`，默认 `MANUAL`，精确映射仓库已知事项。
2. 为历史申请回填目录 `flow_type / item_code`，增加审批意见存储；其后创建申请时按业务代码保存快照。
3. 为工单增加 `flow_archived`，默认 `false`。
4. `service_flow_repair_audit` 按工单主键保存原工单状态、原申请状态、请求流程、修复时间及原因。
5. 对非维修历史工单设置 `flow_archived=true`，在 `service_request_log` 追加 `FLOW_DETACH` 迁移事件。原工单状态、处理人、照片、时间、逻辑删除字段及申请原业务状态全部保留。
6. 运行时维修查询和写入入口同时校验申请快照与归档标记，避免遗漏历史记录再次派单。

已批准或已销假请假仍以原 `service_request.status / leave_cancel_at` 为准，迁移不把历史错误待派工单升级为真实维修完成，也不伪造审批/销假。未知自定义事项需管理员在新配置中显式选择流程，默认人工受理。

### 执行与核对

本阶段的迁移与补偿验证使用隔离测试数据库，未操作当前 9000 服务、现有模拟器或生产数据。后续对目标环境执行时，由正常应用升级流程让 Flyway 应用 V109；先完成数据库备份及迁移预检。迁移已经应用的环境不得手工再次执行整个 V109。

补偿脚本为 [`tools/service-flow/reconcile_nonrepair.sql`](../../tools/service-flow/reconcile_nonrepair.sql)，只能用于已成功应用 V109 的数据库。脚本只补建缺失审计和 `FLOW_DETACH` 事件，并将非维修申请关联工单的 `flow_archived` 从 `false` 改为 `true`；不重新映射目录或申请流程，不改申请业务状态，也不删除工单。它没有内置事务提交，应由执行会话控制事务。

执行前先核对候选记录与迁移事件的确定性 ID。下面第一条查询列出尚未归档或缺少审计、事件的非维修工单；第二条应返回零行，表示 `-work_order_id` 未被其他日志占用。脚本包含逻辑删除的历史工单，不会改变它们的 `deleted` 值。

```sql
SELECT w.id AS work_order_id, w.request_id, r.flow_type,
       w.status AS work_order_status, r.status AS request_status,
       w.flow_archived, w.deleted, a.work_order_id AS audited_work_order_id,
       l.id AS detach_log_id
FROM work_order w JOIN service_request r ON r.id = w.request_id
LEFT JOIN service_flow_repair_audit a ON a.work_order_id = w.id
LEFT JOIN service_request_log l ON l.id = -w.id
WHERE r.flow_type <> 'REPAIR'
  AND (w.flow_archived = FALSE OR a.work_order_id IS NULL OR l.id IS NULL);

SELECT w.id AS work_order_id, l.id AS occupied_log_id, l.action
FROM work_order w JOIN service_request r ON r.id = w.request_id
JOIN service_request_log l ON l.id = -w.id
WHERE r.flow_type <> 'REPAIR'
  AND (l.action <> 'FLOW_DETACH' OR l.request_id <> w.request_id
       OR l.work_order_id IS NULL OR l.work_order_id <> w.id);
```

在仓库根目录打开已选定目标库的 MySQL 客户端，完成备份及以上核对后，在同一会话顺序执行：

```sql
START TRANSACTION;
SOURCE tools/service-flow/reconcile_nonrepair.sql;
-- 保持事务打开，执行下文核对查询。
```

核对结果符合预期后执行 `COMMIT;`，否则执行 `ROLLBACK;`。

脚本允许顺序重复执行：审计按工单主键排重，迁移事件按确定性负 ID 排重，归档更新只匹配尚未归档工单。无新增候选记录时，第二次执行不应增加审计或事件数量，不应改写首次保存的原状态与修复时间。它也能补齐中断后缺失的审计、事件或归档步骤；再次执行前仍应核对目标库与日志 ID。执行过程中若有 SQL 错误，先 `ROLLBACK` 并核对原因，不在错误会话中继续 `COMMIT`。不要并发运行多个补偿会话。

以下查询可在目标库只读核对，不修改业务数据：

```sql
SELECT item_code, item_name, flow_type FROM service_item ORDER BY id;

-- 应返回 0：非维修工单仍被标为有效维修队列。
SELECT COUNT(*) AS non_repair_in_queue
FROM work_order w JOIN service_request r ON r.id = w.request_id
WHERE r.flow_type <> 'REPAIR' AND w.flow_archived = FALSE AND w.deleted = 0;

-- 核对审计快照、归档标记及申请当前业务状态，原单仍保留。
SELECT a.work_order_id, a.request_id, a.request_flow_type,
       a.original_order_status, a.original_request_status,
       w.status AS preserved_order_status, w.flow_archived,
       r.status AS current_request_status, r.leave_cancel_at, a.repair_reason
FROM service_flow_repair_audit a
JOIN work_order w ON w.id = a.work_order_id
JOIN service_request r ON r.id = a.request_id
ORDER BY a.work_order_id;

SELECT request_id, work_order_id, action, comment
FROM service_request_log WHERE action = 'FLOW_DETACH';
```

审计表仅记录历史错误维修关联的修复，不充当审批结果。出现异常时先核对记录、应用版本及流程配置，不通过删除工单、取消逻辑删除保护或整库回滚来恢复错误派单。测试的独立文件回滚证据不等同于数据库线上回滚方案。

### 迁移验证契约

迁移测试应从 V108 开始，插入历史工单后再由 Flyway 应用 V109，并实际执行补偿 SQL 两次。以下是验收要求，执行结果以 `VERIFICATION.txt` 记录为准：

| 验证输入 | 必须观察到的结果 |
|---|---|
| 待审批、已批准、已销假的请假及其他非维修申请关联历史工单 | 工单归档并各保留一条审计、一条 `FLOW_DETACH`；申请状态、销假时间及工单原状态、处理人、照片、逻辑删除值保持原值 |
| 历史已办结但无销假时间的请假、学生已撤回的请假 | 分别显示已办结、已撤回；不显示为已销假，不提供审批或销假操作 |
| 正常维修申请与工单 | 保持未归档，无非维修修复审计或事件，仍可进入维修队列 |
| V109 后补入的遗漏非维修工单 | 第一次补偿建立缺失审计和事件并归档；已有审计不被覆盖 |
| 同一数据库再次执行补偿 SQL | 审计和事件数量及原有内容不变，业务状态不变，非维修有效维修队列数量为零 |
