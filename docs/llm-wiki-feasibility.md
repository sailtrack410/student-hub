# 校园百科（LLM Wiki）可行性分析

针对设想：**LLM Wiki 结果以 Markdown 承载 → 做一个校园百科页面（Vue 文档框架）供学生查阅 → 同一份 Markdown 供 AI 检索 → Agent 综合 RAG 与 Wiki 返回 → 知识库更新后触发 Wiki 生成**。

先给结论，再逐条分析。

## 一、总体结论

**整体可行，架构方向正确——"一份内容、两种消费（人读 + 机读）"是这个方案最有价值的地方。** 定位为 **AI 自主维护 + 人工可校对**（而非人工主编），这个选择让方案更契合本项目，但也把风险从"内容没人写"移到了"错误内容无人发现即固化"。有三处需在动工前明确：

1. **不要新建第二个前端工程。** 管理台没有 Node 构建链（CDN Vue），引入 VuePress/VitePress 会新增一条独立构建管线与部署单元，与现有部署方式冲突。建议用**现有 CDN Vue + 一个 markdown 渲染器**实现百科页。
2. **AI 自主维护要求"文档变更触发"与"提问驱动"并存**，二者职责不同（前者保一致、后者补覆盖），不是二选一。但 AI 自主维护有**七个缺一不可的技术前提**，否则会产生幻觉固化与版本失控。详见 2.5。
3. **纯 Markdown 检索会退步。** Markdown 有结构但**没有向量**；直接把 md 丢给检索等于放弃语义召回，正好丢掉你想提升的部分。Wiki 必须**既存 Markdown 也建向量索引**。

> 修正说明：本文早前版本判定"知识库更新触发 Wiki 生成"为方向错误。该判断在"人工主编"前提下成立，但在 **AI 自主维护**前提下不成立——文档变更正是 AI 维持条目与原文一致的核心触发源。已按后者重写 2.5。

## 二、逐项可行性

### 2.1 Markdown 作为载体 —— 可行，且与现有习惯一致

| 检查项 | 现状 | 结论 |
|---|---|---|
| 项目是否已有 Markdown 语料习惯 | 评测语料 `docs/rag-eval/corpus/*.md` 全是 Markdown | 一致 |
| 小程序侧渲染能力 | `student-hub-weapp/utils/markdown.js` 已有轻量 md→HTML | 可复用思路 |
| Java 侧渲染能力 | **无**（无 commonmark/flexmark 依赖） | 需新增或前端渲染 |
| 文档切分能力 | `KnowledgeDocumentParser` 已支持 `md` 解析（按 `#` 标题分节） | **可直接复用** |

**关键优势**：RAG 现有 `parseText()` 已能解析 Markdown 并按标题切分。也就是说 **Wiki 的 Markdown 可以当作普通知识库文档直接入库**，检索链路零改造。这正是你设想里"AI 检索 markdown"的捷径。

**注意**：`parseText` 只按 `#{1,6}` 单层切分，不建层级（父子）关系。百科页面需要目录树，检索希望有层级上下文——两者都要求分块器升级（见第一节 RAG 方案的"结构感知分块"）。

### 2.2 校园百科页面 —— 可行，但有技术选型阻力

**阻力一：前端形态。** 现状是：

- 管理台 `static/admin/`：CDN 加载 `vue.global.prod.js` + Element Plus，**无 npm/无打包**
- 大屏 `static/screen/`：原生 HTML + 本地 vendored ECharts
- 全仓库**没有任何 `package.json`**

引入 VitePress/VuePress 意味着：新增 Node 构建链、新增产物目录、CI/部署要加一步、Docker 镜像变更。**为了一个百科页付出的工程成本过高，且与项目"优先使用框架自带能力、禁止隐式下载未锁定版本依赖"的约定相悖**（见 CLAUDE.md 依赖原则）。

**替代方案（推荐）**：沿用管理台同款 CDN Vue，加一个 markdown 渲染库（如 `marked` + `DOMPurify`，本地 vendor 到 `static/vendor/`）：

- 与现有部署完全一致，不动构建链
- 渲染器需 **XSS 防护**（DOMPurify）——百科内容虽由管理员维护，但搜索引擎/审计不区分，HTML 注入必须在渲染层阻断
- 若坚持用 Vue 文档框架，可行但需接受多一条构建管线；建议作为独立决策，不与本次功能耦合

**阻力二：内容从哪来。** 页面要"自己维护"，就必须有后台编辑器。现有 `ai_knowledge_base` 只有文档上传（上传 md/pdf 文件），没有"在线编辑单篇条目"的能力。需要新增：
- `wiki_entry` 表（标题、slug、Markdown 正文、版本、状态、可见性、排序）
- 管理端编辑页（Markdown 编辑器 + 预览）
- 公开只读接口 `GET /api/public/wiki/**`（免登录，与 `/screen/**` 同模式）

**已有先例可循**：`screen_notice`（V35）就是"后台维护内容 → 大屏公开展示"，百科可以直接复制这个模式，风险低。

**阻力三：权限边界。** 知识库现有 `visibility`（INTERNAL/PUBLIC）已能覆盖"学生可查 vs 仅内部"。百科页只暴露 PUBLIC，与现有 `PublicKnowledgeController` 的校验逻辑一致，**无需新权限模型**。

### 2.3 同一份 Markdown 双消费（人读 + 机读）—— 可行，是这个方案的核心价值

这是**最值得肯定的一点**。当前知识库的痛点正是"内容为检索而存、人不可读"：上传一个 PDF，学生想自己看只能去翻原文件。让内容同时具备两种形态，收益是：

- 学生能直接查阅（减少"问 AI"的低价值请求）
- AI 检索到的片段能**回链到百科页**，答案可溯源，人可继续深读
- 内容只有一份，**不存在两套内容不同步**的问题

实现上要注意 **单一数据源**：Markdown 正文只存一份（建议存在 MySQL 的 `wiki_entry.content`），向量索引从它派生。**不要**在文件存储和数据库里各存一份，否则必然分叉。

### 2.4 Agent 综合 RAG + Wiki —— 可行，但"综合"要定义清楚

你说的"综合结果返回"是正确方向，但需明确融合方式，否则会出现**两路结果打架**。建议分级而非平均融合：

```text
提问
 ├─ Wiki 直查（条目级，语义匹配）
 │    命中 → 直接作为最高优先级上下文（人工校订过，可信度最高）
 │
 ├─ RAG 检索（片段级）
 │    负责 Wiki 未覆盖的长尾、细节、原文引用
 │
 └─ 合并：Wiki 条目优先 + RAG 片段补充，冲突时以 Wiki 为准并标注来源
```

实现点是现成的：`AiConversationServiceImpl` 已经通过 `KnowledgeBaseService.assistantContext(question)` 注入上下文（第 139 行附近）。只需让它返回**带来源类型标记**的上下文，生成侧提示词区分"已审校条目"与"原始片段"。改动集中在 `RetrievalService` 一处。

**风险**：Wiki 条目由模型生成，其可信度**取决于闸门结果与校订状态**。已过闸门（引用可溯源）或已人工校订的条目，优先级高于原始片段；未过闸门的只能作为普通片段参与，**不得标注为"百科权威内容"**。分级策略的前提正是条目上带有 `gate_result` 与 `review_state` 字段。

### 2.5 AI 自主维护的触发与写入链路 —— 可行，但有七个前提

设定为 **AI 自主维护、人工可校对**（校对是可选动作，不是流程必经环节）。这个定位的逻辑是通的：校园政策文档长尾、更新频繁，靠人工主编维护必然滞后；让 AI 承担日常工作、人只在必要时介入，是正确的分工。

但它把核心风险改变了：**从"内容没人写"变成"错误内容无人发现即被固化"**。因为校对是可选的，AI 的产出可能直接面对学生。所以链路必须自带质量闸门，以下七点缺一不可。

#### 前提一：来源锚定（最容易被忽略，也最重要）

每条条目必须携带**来源引用**（`source_doc_ids` + 各来源的内容哈希）：

- 无来源的条目 = 模型自由发挥 = 幻觉温床，**不允许发布**
- 有来源哈希才能判断"原文改了，这条是否过期"
- 生成时必须能回答"这句话出自哪篇文档哪一段"

这是判断 AI 产出可信度的**唯一客观依据**——不依赖人工读一遍。

#### 前提二：双触发并存，职责不同

| 触发源 | 职责 | 动作 |
|---|---|---|
| **文档变更**（保证一致性） | 原文改了，条目必须跟着改 | 哈希比对定位受影响条目 → 增量重生成 |
| **高频提问**（保证覆盖面） | 学生问的、条目里没有的 | 聚类 → 立项新条目 |
| 定时巡检 | 兜底 | 扫描孤儿条目（来源已删）、冲突条目 |

二者**都需要**，不是二选一：前者防"条目与原文不一致"，后者防"条目覆盖不到真实提问"。你原先设想的"知识库更新后触发"，正是左列那一环。

**去重要求**：生成前先按语义相似度检索已有条目，相似度高于阈值时走"更新"而非"新建"，否则同一主题会裂成多条碎片。

#### 前提三：自动发布闸门（因为校对是可选）

既然校对不是必经流程，就必须有**机器判据**决定条目能否直接发布：

| 闸门 | 判据 | 不通过时 |
|---|---|---|
| 引用覆盖 | 每个论断都能在来源中找到依据 | 退回重生成 |
| 无来源检测 | 条目未引入原文没有的事实（如编造电话号码、日期） | 拒收 |
| 冲突检测 | 与同主题现条目无矛盾 | 转人工 |
| 置信阈值 | 自评 + 引用覆盖率达标 | 转人工校订队列 |

**低于阈值的必须进人工队列，不能静默发布。** 学生端看到的内容一旦标上"百科"就意味着权威，宁可少发不可错发。

#### 前提四：版本与可回溯

- 条目保留版本快照，AI 每次改写都能 diff 出"改了什么"
- 支持一键回滚到任一版本
- 记录生成模型、提示词版本、触发原因（哪篇文档变了 / 哪个问题被高频问）

否则 AI 反复改写后无法追责，也无法判断"这次改动是不是变好了"。

#### 前提五：幂等与并发控制

文档变更事件可能连续触发（批量上传、Flyway 迁移）。若不做防抖与幂等，会出现同一文档生成多条、或并发重复写入。

- 按"条目 + 来源哈希"做幂等键
- 事件按文档聚合、延迟批量处理，避免 N 篇文档触发 N 次全量重算

#### 前提六：成本与配额

LLM 调用不能无上限。需按次/按日限额、单次 token 预算、失败重试退避。文档批量更新时尤其要防止"全量重生成"——必须走前提一的哈希比对做增量。

#### 前提七：可观测与人工介入入口

- 每次生成落日志（触因、输入、输出、闸门结果、耗时）
- 管理端要有**校订队列**：AI 产出中未过闸门的、被标记待复核的，集中呈现待办
- 提供"人工改写"入口——人的修改应优先于 AI 后续的自动重生成（避免人的修正被 AI 覆盖）

#### 一个必须承认的矛盾

**AI 自主维护与"内容准确性"存在天然张力。** 校园政策类内容（请假审批权限、报修时效、收费标准）错一个字就是错，学生据此办事会直接受损。所以务实的定位是：

- **高风险内容**（政策条款、时限、金额、审批权限）：AI 生成草案，**必须人工确认才发布**
- **低风险内容**（办事流程介绍、常见问题、地点指引）：AI 可自动发布，事后抽检 + 学生反馈纠错

按内容风险分级，而不是一刀切"全自动"。这也让"人工校对"落在真正需要它的地方，而不是成为瓶颈。

### 2.6 与检索的融合

见 2.4。补充一点与本节相关的：条目带**闸门结果与校订状态**后，检索侧的分级策略才有依据——已过闸门/已校订的条目排在 RAG 片段之前，未过闸门的只作为普通片段参与（不可标注为"百科权威内容"）。

## 三、改造量评估

| 模块 | 内容 | 复杂度 |
|---|---|---|
| 表结构 | `wiki_entry` + `wiki_entry_version`（版本快照）；字段含 `status`、`review_state`、`source_refs`（文档ID+哈希）、`gate_result` | 中 |
| 生成链路 | 触发编排（文档变更 + 问题聚类）、哈希比对增量、去重、幂等 | **高** |
| 质量闸门 | 引用覆盖校验、无来源检测、冲突检测、置信评分 | **高** |
| 管理端 | 条目列表 + 校订队列 + Markdown 编辑器 + 预览 + 版本 diff/回滚（沿用 CDN Vue） | 中 |
| 公开接口 | `GET /api/public/wiki/**`（免登录，仿 `PublicKnowledgeController`） | 低 |
| 百科页面 | `static/wiki/index.html` + CDN Vue + marked/DOMPurify（本地 vendor） | 中 |
| 检索接入 | Wiki 条目入库建向量，`assistantContext` 分级合并 | 中 |
| 分块升级 | `parseText` 支持层级，供目录树与检索共用 | 中 |

**分期建议**（相对早前版本调整，因为 AI 自主维护的闸门与版本是必须项而非可选）：

- **一期**：`wiki_entry` + 版本表 + 管理端编辑/校订 + 公开百科页 + 入库参与检索。此期由人工创建条目，**但表结构与状态机预留 AI 写入位**，避免二期改表。
- **二期**：文档变更触发的增量重生成 + 质量闸门。
- **三期**：高频提问聚类 → 新条目立项 + 低风险内容自动发布。

**不建议一次性做全自动发布**：闸门（前提三）与版本（前提四）没建好之前，自动发布等于无人兜底地把幻觉推给学生。

## 四、需要你决策的三个点

1. **前端形态**：接受"CDN Vue + marked"（改动小、与现有一致），还是要引入 VitePress 单独构建（好维护但要加构建链）？
2. **发布闸门的分级线画在哪**：AI 自主维护 + 校对可选的前提下，哪些内容允许**自动发布**？建议高风险（政策条款、时限、金额、审批权限）一律人工确认，低风险（流程介绍、常见问题）自动发布 + 抽检。你若希望更激进的全自动，需要接受幻觉直接面向学生的风险。
3. **是否并行修 RAG 召回**：前面实测口语化提问 R@1=0.000。Wiki 能覆盖**高频**问题，但**长尾**仍靠 RAG——这部分不修，Wiki 只是绕过而非解决。建议 Wiki 与 RAG 召回修复并行，而非用 Wiki 替代。

## 五、与既有规划的关系

本方案是 `docs/rag-retrieval-plan.md` 的**补充层，不是替代**：

- RAG 负责**覆盖面**（长尾、细节、原文引用、时效性）
- Wiki 负责**高频问题的确定性**（口径稳定、可人工校订、可溯源）
- 两者共享同一份 Markdown 内容与同一套向量索引，通过分级融合而非并行竞争

不建议用 Wiki 整体替代 RAG：政策文档会持续修订，全量重编译的维护成本高，而 RAG 的"改完即生效"是已经用上的优势。
